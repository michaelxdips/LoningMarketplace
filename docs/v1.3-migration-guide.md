# V1.3 Migration Guide

## Official command

```bash
npm --prefix backend run db:migrate
```

Do not run SQL migrations selectively, modify `drizzle.__drizzle_migrations` manually, or reset shared data.

## Sequence

The official command executes this contract:

1. Apply registered SQL migrations before `0008`.
2. Run `preparePublicIntegrity()` in its own PostgreSQL transaction.
3. Apply `0008_finalize_public_integrity` through the Drizzle migration transaction.
4. Run `assertPublicIntegrity()` against the final database state.

## Recovery classification

**RECOVERABLE IDEMPOTENT PREPARATION**

Preparation and migration `0008` use separate transactions. A forced failure inside migration `0008` proved that prepared UMKM and product slugs remain committed while all `0008` schema changes and its ledger record roll back. The official command can then be rerun after removing the failure condition. Deterministic canonical slugs remain unchanged, no extra suffix is allocated, `0008` is recorded exactly once, the final assertion passes, and `db:audit` passes.

This is not a fully atomic preparation. Operators must not describe it as one.

## Refusal behavior

Migration stops without recording `0008` when it finds:

- duplicate non-empty product slugs;
- duplicate non-empty UMKM slugs;
- an invalid WhatsApp number outside `^628[0-9]{7,12}$`.

Failures report a bounded count and row IDs. Resolve the conflicting data deliberately; do not delete rows or rewrite the migration ledger to bypass the refusal.

## Rerun and audit

A successful rerun is idempotent. Existing non-empty canonical slugs stay unchanged and missing slugs use the shared deterministic allocator.

After migration, run:

```bash
npm --prefix backend run db:audit
```

The audit must report `Audit Status: PASS`. Verify that both phone constraints are present with `convalidated=true` before production traffic.

Never use a destructive database reset on shared or production data.
