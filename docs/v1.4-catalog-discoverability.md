# V1.4 catalog discoverability

**Status:** integrated V1.4 source contract
**Measured at:** 2026-07-30 (Asia/Jakarta)
**Repository revision:** `b57d12564017507a24dd534648ae769cc732aeff`

This document describes the integrated V1.4 discoverability behavior. Runtime verification results remain evidence in the final phase report rather than claims in this contract document.

## Public catalog entry points

The API is mounted under `/api` by `backend/src/app.ts`.

| Capability | Request | Result bound | Visibility |
|---|---|---:|---|
| UMKM directory | `GET /api/umkms?q=kopi&category=Kuliner&limit=100` | `limit` defaults to 100 and is capped at 100 | UMKM must be `published` |
| Product catalog | `GET /api/products?q=kopi&category=Kuliner&umkmId=<uuid>&limit=100` | `limit` defaults to 100 and is capped at 100 | Product and parent UMKM must both be `published` |
| Product detail | `GET /api/products/<slug>` | one item | published product and published parent UMKM |
| UMKM detail | `GET /api/umkms/<slug>` | one item | published UMKM |
| Related-product contract | `GET /api/products/<slug>/related?limit=4` | `limit` defaults to 4 and is capped at 4 | returned candidates require published product and published parent UMKM; current product excluded |

`<slug>` can be the canonical public slug. The API also accepts a legacy UUID identifier up to 128 characters; the frontend detail pages replace a UUID URL with the returned canonical slug while preserving query string and hash.

Canonical URL examples:

```text
https://<site>/produk/keripik-singkong
https://<site>/umkm/dapur-loning
https://<site>/?q=keripik&category=Kuliner
```

The filter URL is shareable. `q` is trimmed and bounded to 80 characters in the frontend and backend. Categories are the enum values `Kuliner`, `Kerajinan`, `Jasa`, `Sembako`, and `Pertanian`; an unknown category is treated as `Semua` by the frontend and rejected by the API. Default state is omitted from the URL.

## Search contract

Search is server-side, case-insensitive substring matching:

```text
pattern = %<escaped q>%
```

The repository uses `ILIKE` and escapes `%` and `_` in the user value before surrounding it with `%`.

| Endpoint | `q` fields | Other filters | Stable ordering |
|---|---|---|---|
| `/api/umkms` | `umkms.name`, `owner`, `description`, `address`, `category` | published status; optional category | `displayOrder ASC`, `id ASC` |
| `/api/products` | `products.name`, `description`, joined `umkms.name`, `products.category` | product and parent published status; optional category and `umkmId` | `displayOrder ASC`, `id ASC` |

The two homepage search inputs share the same URL-owned `q` value. Typing in either **Cari produk lokal** or **Cari pelaku UMKM** updates the URL with replacement, so keystrokes do not flood browser history; Enter or the **Cari** button submits an explicit history entry. The selected category applies to both datasets and creates a restorable history entry.

### Request frequency observed from source

The homepage uses a 300 ms debounce before the search value enters the React Query keys. The logical request graph is:

1. No filter: one `GET /api/products` and one `GET /api/umkms` query are enabled.
2. A settled non-default query: the filtered product and filtered UMKM query identities become enabled. The unfiltered queries remain mounted and enabled in the current `App.tsx`, so a cold transition can involve up to four request identities (two unfiltered plus two filtered). React Query's three-minute `staleTime` can serve cached identities instead of issuing network requests.
3. Each distinct debounced query/category key normally issues one request per resource while its cache is fresh. One retry is allowed for a network/5xx failure; manual refetch is also possible. Each settled 300 ms value can create a new pair of filtered identities.

This is a source-derived request-frequency bound, not a browser waterfall or load-test result. The current code does not add a search analytics event and does not store the raw query.

## Response fields and visibility

Public UMKM list/detail data includes:

- `id`, `slug`, `name`, `owner`, `description`, `phone`, `category`, `imageUrl`, `address`
- optional `workingHours`
- contact/catalog state fields such as `contactVerifiedAt`, `catalogUpdatedAt`, `isContactValid`, `isContactVerified`, `isContactVerificationFresh`, and `contactVerificationExpiresAt`
- optional media asset metadata when an asset is attached

Public product list data includes:

- `id`, `slug`, `umkmId`, `umkmName`, `name`, `price`, `description`, `category`, `imageUrl`, `isAvailable`
- optional `unit`
- optional media asset metadata when an asset is attached

Product detail includes the product fields plus the public parent UMKM reference `{ id, slug, name, phone }`. `price` is explicitly nullable; `unit` and `workingHours` are optional. The API returns an error envelope for invalid parameters and not-found resources, for example `{ error: { message, code } }`.

No pagination cursor, total-count field, relevance score, or search facets are currently returned. A UI count is the number of items in the bounded response, not the total matching catalog size.

## Related selection and request boundary

The related endpoint performs a fixed two-step repository operation:

1. Resolve the current published product to its `id`, `category`, and `umkmId`.
2. Fetch candidate products in one joined query, excluding the current product and requiring both the product and parent UMKM to be published.

Candidate priority is:

1. same category;
2. then same UMKM;
3. then all other eligible products;
4. `displayOrder ASC`, `id ASC` as tie-breakers.

The response is bounded to four items. The source lookup and every candidate require both product and parent UMKM to be published. `backend/tests/routes.test.ts` covers route validation, bounds, exclusion, and not-found behavior; the isolated integration smoke covers real seeded visibility, uniqueness, and deterministic ordering. `ProductDetailPage.tsx` requests the related endpoint by canonical slug, and `RelatedProducts.tsx` reuses the shared `ProductCard` in a canonical-link-only variant.

### No-N+1 proof boundary

The source review supports these fixed-query properties:

- each public UMKM list is one joined database query;
- each public product list is one joined product/UMKM/media query;
- the related repository path is one current-item lookup plus one joined candidate query, not one query per returned candidate;
- response mapping is in memory over the bounded rows.

This is not a production query-plan or latency proof. Route tests use a repository test double, not PostgreSQL. No `EXPLAIN (ANALYZE, BUFFERS)`, production cardinality measurement, or concurrent load test was run in this documentation task. The product detail frontend currently makes a product request and then a separate parent-UMKM request; that is a fixed two-request detail flow, not an N+1 candidate loop.

## Accessibility behavior

Current discoverability controls provide:

- explicit screen-reader labels for both search inputs;
- `aria-pressed` state on category buttons and an `aria-label` on the category group;
- polite `aria-live` result counts for product and UMKM lists;
- keyboard-visible focus rings and minimum touch-target sizing on interactive controls;
- semantic links for canonical product and UMKM pages;
- accessible breadcrumb and related-section labels in the detail/related components;
- focus restoration and route-main focus management for detail/dialog navigation.

Known interaction limit: because both search fields share `q`, assistive-technology users receive one combined filter state even though two inputs are visible. The current list does not expose a total-match count beyond the returned bounded array.

## SEO and sharing contract

- Filter state is encoded in the shareable homepage URL, for example `/?q=keripik&category=Kuliner`.
- Entity pages use canonical slug routes `/produk/<slug>` and `/umkm/<slug>`.
- Legacy UUID detail URLs are accepted and client-canonicalized to the slug after the API response.
- `usePageMetadata` creates route metadata, canonical, Open Graph, Twitter, and JSON-LD tags in the browser.
- The canonical builder uses `window.location.pathname`, so filter query parameters are intentionally not included in the canonical URL. A filtered homepage URL remains shareable, but its canonical points to the unfiltered homepage path.
- `frontend/index.html` is a root shell and `frontend/src/main.tsx` mounts the application; there is no server-side rendering claim. Initial HTML does not contain catalog entities or route-specific product/UMKM metadata. Metadata and JSON-LD are client-side behavior.
- `frontend/public/robots.txt` allows `/`; no sitemap or filter-specific crawl policy is present.

## Analytics and privacy decision

Current public events are limited to `umkm_view`, `product_view`, `inquiry_started`, `message_copied`, and `whatsapp_opened`. Events carry a UUID anonymous session ID, source, and optional public target IDs. The event schema is strict; it has no raw query field. Public-event deduplication uses a five-minute bucket and unique target/source/session keys. The admin consumer currently reports inquiry and view metrics; it has no search-query report.

**Decision: do not add a search event in V1.4 documentation or source.** A new event is justified only after all of these are proven:

1. an identified operational consumer and decision it supports;
2. a retention/deletion policy and access boundary;
3. a privacy review showing that raw `q` is not stored or exposed;
4. a dedupe rule that prevents repeated typing/cache retries from inflating counts;
5. a stable event version and target/source contract;
6. rate-limit and storage-volume capacity for the new event.

The current implementation satisfies the raw-query minimization requirement by sending no search event and storing no raw `q` in `public_events`.

## Scalability ceiling and trigram trigger

The current `ILIKE '%q%'` predicates are appropriate for a small village catalog but are not a demonstrated large-catalog search design. A leading wildcard generally prevents ordinary B-tree indexes from making arbitrary substring search cheap. The current `limit` bounds returned rows, not the number of rows PostgreSQL may inspect.

No numeric catalog-size ceiling is claimed here because no production cardinality, query plan, or latency budget was supplied. Trigger the next search-scale investigation when observed `EXPLAIN (ANALYZE, BUFFERS)` plans show sustained broad scans, or when measured search p95/DB CPU crosses the service's agreed budget under representative catalog load. At that trigger, evaluate `pg_trgm` GIN/GiST indexes and query-shape changes through a separately reviewed migration. No migration is proposed or added by this documentation task.
